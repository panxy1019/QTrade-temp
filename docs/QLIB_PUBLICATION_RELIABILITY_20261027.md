# 统一行情发布链路可靠性修复（2026-10-27）

## 问题与边界

生产网页 `https://q-trade-temp.vercel.app/` 已部署统一 1,500 目标证券的只读行情接口和页面职责调整，但首次批量发布及后续普通 Git 推送超过 90 秒。网页的数据身份与逐行校验通过时，发布物仍可能过期，必须继续显示 `STALE_PUBLICATION`。

采集、历史回补、正式日版本、预测和前向账本与网页发布分别运行。发布故障不能解释为停止采集，也不能通过改写行情时间、实验时间或放宽新鲜度阈值解决。PAPER 不因本轮发布修复重启或再次恢复。

## 已核实的原因

1. 实际集群 Git 上行约 25—39 KiB/s。此前两次受控追赶完整周期耗时 541.17 / 280.60 秒，其中推送耗时 466.03 / 228.62 秒；它们不是普通周期达标证据。
2. 单纯采用内容哈希文件名时，Git 难以稳定识别同一证券、频率和会话的增量内容。新增稳定身份路径作为已有不可变对象的硬链接，有助于差分压缩；行情接口仍引用原内容哈希路径。
3. 第一次元数据种子推送仍在 600 秒内未完成。独立核验发现 Git 默认稀疏对象遍历把已公开的 4,488 个行情对象也重新打包。它不是新增行情或原始数据缺失。

真实集群、相同种子和相同排除父版本的本地打包对照：

| 遍历设置 | 包字节数 | 包内对象数 | 种子新增行情 blob |
| --- | ---: | ---: | ---: |
| `pack.useSparse=true` | 10,718,392 | 4,495 | 0 |
| `pack.useSparse=false` | 169,904 | 7 | 0 |

后者只发送新增提交和目录元数据，减少约 98.4% 的传输字节。真实版本、对象计数、包哈希和运行时钟保存在签名实验记录中。Git 官方文档说明，稀疏遍历在新增路径等情况下可能包含额外对象：[pack.useSparse](https://git-scm.com/docs/git-config#Documentation/git-config.txt-packuseSparse)。

另一个 **合成的** 1,500 证券下一帧实验从 3,679,943 字节降至 714,097 字节，说明稳定身份路径对后续增量的作用。它不代替实际远端推送、盘中下一帧或网页新鲜度验收。

## 实现与操作约束

- `publish_unified_market.py` 保留不可变权威对象，增加同内容稳定路径；种子模式读取已公开版本，不导出新数据，也不重写索引内容、时间或修改时间。
- `bootstrap_public_aliases.py` 默认只生成计划；实际应用要求发布服务 PID 为零、固定公开仓库、`main` 分支和干净的已跟踪文件。它创建备份引用、使用隔离索引和非强制推送，保存检查点，保留原历史与未跟踪文件。
- 两个 Git 执行器均使用单条命令范围的 `-c pack.useSparse=false`，不改写全局或仓库配置。普通命令仍限 90 秒，显式种子推送限 600 秒，并清理自身进程组。
- 第一次超时记录保留。超时后重新核对了远端和本地均为 `332efcf84f32bbe65fdc53152ac2ae50aed4a17c`、已跟踪文件干净，再使用独立报告路径重试。
- 集群 `79141f4` 针对真实 Git 对象打包、初始化、行情接口和进程组清理的测试为 **95 通过、1 项 Windows 专用跳过**。

还发现跨 Python 进程的字段插入顺序变化会让语义相同的 4,488 个碎片全部获得新字节哈希。现固定字段顺序，并用多个 `PYTHONHASHSEED` 的真实子进程测试证明相同输入的字节稳定；新增加的真实 Bar 只改变所属碎片。实际一次性格式迁移对比确认 **4,488 / 4,488 份 JSON 语义完全相同**，原文件全部保留。受控首次导出耗时 47.05 秒（显式 120 秒上限），格式推送耗时 242.78 秒（600 秒上限）；普通导出仍限 45 秒、Git 命令仍限 90 秒。

发布循环现以两次启动间隔计时，工作时间消耗间隔，避免完成导出与推送后又等待完整 60 秒。循环保持顺序，不重叠。

## 可重复的公网抽查

固定来源的只读工具已纳入仓库。将下列占位符替换为实际已审阅、已部署的 `main` 40 位 Git 身份，报告路径必须尚不存在：

```powershell
$env:PYTHONPATH='E:/QTrade-git/src;E:/QTrade-git'
$env:LIVE_TRADING_ENABLED='false'
python -m scripts.probe_unified_publication --expected-production-revision REVIEWED_40_HEX --report NEW_REPORT.json
python -m pytest tests/test_probe_unified_publication.py tests/test_qlib_public_delivery.py -q
```

工具校验生产身份、完整 1,500 目标与 3,000 索引条目，并将五个固定样本接口的所有返回 Bar 与对应公开不可变碎片逐行比较。它分别报告 180 秒索引发布新鲜度、1,200 秒目录新鲜度及实际数据覆盖，不把 `FRESH_TRANSPORT` 解释成全池完整。样本覆盖股票、ETF 缺口与无数据案例，不能据此声称所有 4,488 个公开碎片都经过公网重新读取。

仅允许固定 HTTPS 来源及 GET，限制响应大小、请求数量和总耗时，拒绝跳转、压缩/长度异常、身份漂移、校验错误，以及声明实盘或晋级权限的发布物。报告保留实际捕获时钟、大小、哈希和校验身份；不重复存储完整目录正文，是紧凑抽查凭证。新鲜有效结果退出 0；有效但过期结果保存为过期并退出 2；完整性、传输或版本漂移退出 1，不创建通过凭证。版本在读取期间变化时应重新检查当前部署并重试，不能使用旧数据兜底。

固定不可变 commit 的 raw 目录、索引和样本碎片请求支持 `gzip, identity`，API 请求继续使用 `identity`。传输字节与解压后的原始 Git 文件字节各自受同一资源大小上限约束；流式解压限制单次输出分配，并在每次读取、解压及 EOF 后检查原总截止时钟。拒绝截断、尾随数据、多个 gzip member、未知编码、校验失败和传输 Content-Length 不符。报告新增 `transport_body_bytes`、`content_encoding`；原 `body_bytes`、`body_sha256` 和目录 Git blob 身份仍绑定精确解压字节。180 秒总探针预算、25 请求、48 MB 累计解压捕获量及 180/1,200 秒新鲜度阈值不变；此支持本身不代表新的生产性能验收。

12:53 的[真实公网抽查](evidence/qlib-publication-live-probe-4cee136-20261027.json)固定生产 `4cee136`，索引和目录年龄分别为 119.071 / 123.200 秒，均通过原新鲜度门限。覆盖仍为 `PARTIAL`，且已知缺口与无数据样本如实返回。该工具及既有公开交付校验在真实 Linux `34bba7c` 上 [95 项通过、无跳过](evidence/qlib-publication-probe-linux-34bba7c.xml)。[汇总凭证](evidence/qlib-publication-rollout-20261027.json)记录各独立证据的原字节哈希，保留早先的失败凭证。
